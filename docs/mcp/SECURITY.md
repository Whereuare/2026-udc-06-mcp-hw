# Threat model MCP-інтеграцій (Task C)

## 1. Що до чого має доступ

| Сервер | Дані/ресурси, до яких дістає | Секрети | Може писати? | Довіра до автора |
|---|---|---|---|---|
| **filesystem** | у Claude Code — **увесь репо** (хост передає `roots`, вони замінюють аргумент `./app/data`); у хостах без roots — `./app/data` | немає | сервер — **так** (`write_file`, `edit_file`, `create_directory`, `move_file`); у Claude Code заблоковано `permissions.deny`* | офіційний (@modelcontextprotocol) |
| **memory** | файл `<репо>/.mcp-memory.jsonl` (`MEMORY_FILE_PATH`, у `.gitignore`), персистентний між сесіями | немає | так — лише у свій файл графа | офіційний (@modelcontextprotocol) |
| **catalog** | код `app/dist/index.js`; дані — `app/data/catalog.json`, який читає `loadCatalog()` | немає | ні | свій код |

*Deny-правила в `.claude/settings.json` діють лише в Claude Code. Сам сервер
режиму read-only не має, тож у Cursor/VS Code з тим самим `.mcp.json` запис буде доступний.

## 2. Ризики, які я вважаю реальними для цієї конфігурації

### Prompt injection через дані ✓ МІЗЕРНИЙ

- **Що може статися:** Синтетичні товари в `catalog.json` — це static локальні дані без користувацького введення. Жоден з трьох серверів не тягне контент ззовні (веб, тікети, користувацькі файли).
- **Реальність ризику:** Мінімальна. Агент читає лише заповнені розробниками дані, які під контролем.
- **Нюанс:** filesystem у Claude Code бачить увесь репо, а memory зберігає граф між сесіями. Якщо в репо потрапить файл із текстом, адресованим агенту, і агент збереже його в memory, такий текст переживе сесію. Тому граф у `.gitignore` і чиститься вручну.

### Занадто широка область доступу ✓ ЗМЕНШЕНА

- **Filesystem:** задумано `./app/data`, але в Claude Code фактичний scope — **корінь репо**: хост відповідає на `roots/list` каталогом сесії, і сервер замінює ним аргумент (перевірено: `list_allowed_directories` → корінь репо). Не домашня тека і не `/`, але агент може читати будь-який файл репо, зокрема `.env`, якщо він з'явиться локально.
- **Memory:** **не** сесійна і **не** ізольована між чатами — граф пишеться у `.mcp-memory.jsonl` і доступний усім наступним сесіям у цьому репо. Без `MEMORY_FILE_PATH` він лежав би в кеші npx і був би спільним для всіх проєктів на машині; тепер він обмежений цим репо.
- **Catalog сервер:** Дає доступ лише через функції `searchProducts`, `findBySku`, `lowStock`, `categories`, `inventoryValue` — не прямо до файлової системи.

### Витік секретів ✓ НЕ ЗАСТОСУЄТЬСЯ

- Нема ніяких токенів у цій конфігурації. Усі сервери — безкоштовні, публічні.
- `.env` у `.gitignore`; у репо лише `.env.example`.
- Ніякого поточного секрета не потрапило у git (перевірено: `git grep -nE "ghp_|github_pat_|sk-"`).

### Зміна поведінки сервера після встановлення ⚠️ ПРИЙНЯТИЙ РИЗИК

- **Поточне:** `npx -y` без фіксованої версії — завжди завантажує `@latest`.
- **Ризик:** Якщо `@modelcontextprotocol/server-filesystem` оновиться з помилкою, агент розпочне невіджаче через невідповідний API.
- **Припустиме для домашки:** Проєкт навчальний, не production. Для реального використання слід фіксувати версії в `package.json`.

### Дії з побічним ефектом ✓ ВИКЛЮЧЕНА

- Усі tools у custom серверу **read-only**:
  - `search_inventory()` — лише пошук
  - `check_stock()` — лише читання
  - `low_stock()` — лише список
  - `catalog_summary()` — лише статистика
- Filesystem **не** інертний: сервер має 4 write-tools. В Claude Code вони заблоковані `permissions.deny` (перевірено: виклик `write_file` відхилено хостом). Це захищає й `app/data/catalog.json` — ground truth для Task D.
- Memory пише лише у власний файл графа; на інші файли впливу немає.

## 3. Що я зробив, щоб це зменшити

Конкретні кроки у цьому репо:

- **Filesystem scope:** аргумент `./app/data` у `.mcp.json` діє лише для хостів без `roots`. У Claude Code реальна межа — корінь репо (каталог сесії); це перевірено й записано в `docs/mcp/servers.md`. Ні аргумент, ні `roots` не є межею безпеки.
- **Filesystem write-tools заблоковано на рівні хоста:** `.claude/settings.json` → `permissions.deny` для `mcp__filesystem__write_file`, `edit_file`, `create_directory`, `move_file`.
- **Шляхи прив'язані до кореня проєкту:** усі сервери запускаються через `sh -c 'cd "$CLAUDE_PROJECT_DIR"; exec …'`, тому scope і шлях до `server.js` не залежать від cwd хоста.
- **Memory ізольовано в репо:** `MEMORY_FILE_PATH=<репо>/.mcp-memory.jsonl`, файл у `.gitignore`, тож граф не потрапить у git.
- **Custom сервер — read-only:** Жодного tool не записує, не видаляє, не надсилає. Логіка імпортована з `app/dist/` (протестована, під контролем).
- **Немає зовнішніх джерел:** filesystem дістає лише локальні файли; memory ізольована; catalog не делегує на сторонні API.
- **Секрети захищені:** `.env` у `.gitignore`, конфіг не містить літеральних ключів.
- **Версіонування:** Офіційні сервери (@modelcontextprotocol) від організації, що підтримує MCP SDK. Не community packages, не знайдені в npm.

## 4. Що лишилось прийнятим ризиком

- **Floating versions (`npx -y @latest`)** — сервери можуть оновитися автоматично без оцінки змін. Припустиме для домашки; в production варто зафіксувати.
- **Відсутність криптографічної перевірки коду:** Довіра до репутації Anthropic та npm реєстру, але без GPG-підписів. Припустимо для PoC.
- **Немає межі на рівні ОС.** Сервери працюють від мого користувача без пісочниці. Filesystem у Claude Code бачить увесь репо, а deny-правила — лише механізм хоста: в іншому хості або при помилці в правилах сервер зможе писати в межах репо. Для домашки з синтетичними даними й без `.env` це прийнятно; для реальних даних — окремий користувач або контейнер з read-only mount `app/data`.
- **Memory персистентна:** нотатки агента з однієї сесії впливають на наступні (зокрема хибні). Прибирається вручну: `rm .mcp-memory.jsonl`.
